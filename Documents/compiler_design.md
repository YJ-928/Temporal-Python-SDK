# Compiler Design

> **Status:** R&D / Design Phase
> **Purpose:** Deep dive into each of the 5 compiler pipeline stages, their algorithms, special cases, and design trade-offs.

---

## 1. Overview

The compiler is a pure function: `compile(WorkflowGraph) → CompilerOutput`. It has no side effects, no database access, and no network calls. The same input always produces the same output.

```
WorkflowGraph → [Validator] → [Normalizer] → [IR Builder] → [Planner] → [Generator] → CompilerOutput
```

**CompilerOutput structure:**
```json
{
  "graph_json": "...",
  "normalized_graph_json": "...",
  "ir_json": "...",
  "execution_plan_json": "...",
  "dsl_yaml": "...",
  "dsl_json": "..."
}
```

Each field is a string. `graph_json` is the raw input, preserved verbatim. The other five are generated by successive stages.

## 2. Stage 1: Validator

### Purpose

Check the structural integrity of the raw `WorkflowGraph` before any transformation. The Validator loads no templates and performs no value substitution — it only checks graph structure.

### Input
A `WorkflowGraph` JSON object (not yet normalized).

### Output
A `ValidationResult`:
```json
{
  "valid": true | false,
  "errors": [
    { "code": "ERROR_CODE", "message": "human readable", "node_id": "id or null", "edge_id": "id or null" }
  ]
}
```

If `valid` is false, the pipeline halts here. The API returns the `ValidationResult` with HTTP 422.

### Validation Rules

| Rule | Error Code | Trigger |
|---|---|---|
| No `START` node | `MISSING_START` | nodes array has no item with `type: START` |
| More than one `START` | `MULTIPLE_START` | nodes array has >1 item with `type: START` |
| No `END` node reachable from `START` | `MISSING_END` | graph walk from START never reaches an END node |
| Node has no outbound edges and is not `END` | `DANGLING_NODE` | dead end — no path to END |
| Node unreachable from `START` | `UNREACHABLE_NODE` | node id not visited in forward walk from START |
| Self-loop on a non-LOOP edge | `INVALID_SELF_LOOP` | edge.source == edge.target and edge_type != LOOP |
| Cycle detected (excluding LOOP edges) | `CYCLE_DETECTED` | topological sort fails on non-LOOP subgraph |
| `IF` node missing TRUE edge | `MISSING_BRANCH` | IF node has no outbound edge with edge_type TRUE |
| `IF` node missing FALSE edge | `MISSING_BRANCH` | IF node has no outbound edge with edge_type FALSE |
| `IF` node has multiple TRUE edges | `MULTIPLE_BRANCH` | IF node has >1 outbound edge with edge_type TRUE |
| `PARALLEL` node has fewer than 2 non-ERROR outbound edges | `INSUFFICIENT_BRANCHES` | PARALLEL node has <2 SUCCESS outbound edges |
| Edge `source_handle` references a handle ID not in source node's `outputs` | `INVALID_HANDLE` | handle mismatch |
| Edge `target_handle` references a handle ID not in target node's `inputs` | `INVALID_HANDLE` | handle mismatch |
| `task_queue` is empty or contains spaces | `INVALID_METADATA` | field validation |
| `workflow_type` is empty or contains spaces | `INVALID_METADATA` | field validation |

### Algorithm: Cycle Detection

```
Algorithm CycleDetector(graph):
  1. Build directed adjacency list excluding all edges with edge_type == LOOP
  2. Run Kahn's algorithm (BFS-based topological sort) on the adjacency list
  3. If the sorted list has fewer nodes than the graph → a cycle exists → CYCLE_DETECTED
  4. Return the topological order for reuse by the IR Builder
```

Kahn's algorithm is preferred over DFS-based detection because it produces the topological order as a by-product. The IR Builder needs this order anyway.

### Algorithm: Reachability Check

```
Algorithm ReachabilityChecker(graph, start_node_id):
  1. BFS from start_node_id following all outbound edges (including LOOP edges)
  2. Collect visited node ids
  3. Any node not in visited set → UNREACHABLE_NODE
  4. Any END node in visited set → END is reachable
```

## 3. Stage 2: Normalizer

### Purpose

Transform the raw graph into a `NormalizedGraph` by:
1. Filling in default values for optional config fields (per node registry)
2. Resolving missing `source_handle` / `target_handle` from `edge_type` inference
3. Expanding the `task_queue` and `workflow_type` into the output document metadata
4. Removing dead-end nodes that were already flagged but allowed through (defensive — should not happen if validator ran)
5. Numbering unnamed nodes with auto-generated labels

### Input
`WorkflowGraph` (validated, assumed structurally correct).

### Output
`NormalizedGraph` — same structure as `WorkflowGraph` with filled-in values and handle resolutions.

### Default Filling Rules

Each node definition YAML may specify defaults:
```yaml
config_defaults:
  retry: null           # no retry by default
  outputKey: null       # no output key
  export: true          # default: export to $context
```

The normalizer merges these defaults into the node's `config` object, with explicit config values taking precedence.

### Handle Inference

For each edge where `source_handle` is absent:
- `edge_type: DEFAULT` → leave `source_handle: null` (any output)
- `edge_type: SUCCESS` → `source_handle: "success"`
- `edge_type: ERROR` → `source_handle: "error"`
- `edge_type: TRUE` → `source_handle: "true"`
- `edge_type: FALSE` → `source_handle: "false"`
- `edge_type: LOOP` → leave `source_handle: null`

For each edge where `target_handle` is absent:
- All cases → `target_handle: "input"` (all nodes in V1 have a single input handle named `"input"`)

### Auto-Label Generation

If a node has no `label` (null or empty string), the normalizer generates one:
```
"label": "{NodeType} {sequential_index}"
```
Example: `"ACTION 1"`, `"IF 2"`, `"WAIT 3"`. The index is the node's position in the topological order.

This generated label becomes the Zigflow task name in the `do` list.

## 4. Stage 3: IR Builder

### Purpose

Transform the `NormalizedGraph` into a `WorkflowIR` — a tree structure that directly mirrors the nesting of Zigflow tasks. The IR is DSL-agnostic; it knows nothing about Zigflow YAML syntax.

### Input
`NormalizedGraph` + topological order from the Validator.

### Output
`WorkflowIR`:
```json
{
  "task_queue": "...",
  "workflow_type": "...",
  "version": "...",
  "use": { ... },
  "tasks": [ IRTask, ... ]
}
```

Each `IRTask`:
```json
{
  "id": "node_id",
  "name": "task name (from node label)",
  "node_type": "NodeType",
  "config": { ... },
  "subtasks": [ IRTask, ... ],
  "branches": { "true": [ IRTask ], "false": [ IRTask ] },
  "parallel_branches": [ [ IRTask ], [ IRTask ] ],
  "is_error_handler": false
}
```

### Algorithm: Topological Walk

```
Algorithm IRBuilder(normalized_graph, topological_order):
  1. Filter out START and END nodes from topological_order
  2. For each remaining node in order:
     a. If the node is IF:
        - Walk the TRUE-edge path → collect true_tasks
        - Walk the FALSE-edge path → collect false_tasks
        - Find convergence point (first node reachable from both paths)
        - Emit an IRTask with branches: {true: true_tasks, false: false_tasks}
        - Advance the cursor past the convergence point
     b. If the node is PARALLEL:
        - For each SUCCESS-typed outbound edge:
          - Walk the branch path until convergence point
          - Collect branch_tasks
        - Emit an IRTask with parallel_branches: [branch_0_tasks, branch_1_tasks, ...]
        - Advance past the convergence point
     c. If the node is WAIT or ACTION or VARIABLE or WORKFLOW:
        - Emit a flat IRTask with the node's config
  3. Return the tasks list
```

### Convergence Point Detection

For IF nodes: the convergence point is the first node that has an inbound edge from both the TRUE-path and the FALSE-path. This is the node where the two branches rejoin.

```
Detection algorithm:
  1. Walk the TRUE path → collect set of reachable node IDs: true_set
  2. Walk the FALSE path → collect set of reachable node IDs: false_set
  3. Convergence point = first node in topological_order that is in both true_set and false_set
```

Edge case: if the branches never converge (e.g., both go directly to separate END nodes), there is no convergence point. The validator must have allowed this — both branches reach END, which is valid.

For PARALLEL nodes: same algorithm applied to all branch sets simultaneously.

### `use` Block Assembly

The IR `use` block is assembled from retry references found in `config.retry` fields across all ACTION nodes:
- For each ACTION node with a non-null `config.retry` value, collect the retry policy name
- Look up the retry policy definition in `use_retries_registry` (or use inline defaults)
- Assemble the `use.retries` dict

## 5. Stage 4: Planner

### Purpose

The Planner annotates the `WorkflowIR` with execution metadata to produce an `ExecutionPlan`. This plan is used for the `/simulate` API endpoint — it shows what will happen at execution time without actually running anything.

The Planner never modifies the IR structure. It only adds annotations.

### Input
`WorkflowIR`

### Output
`ExecutionPlan`:
```json
{
  "stages": [
    {
      "stage_index": 0,
      "task_name": "fetchUser",
      "node_type": "ACTION",
      "parallelism": 1,
      "is_signal_wait": false,
      "is_timer_wait": false,
      "branch_count": 0,
      "estimated_duration": null
    },
    ...
  ],
  "signal_points": [ { "stage_index": 2, "signal_name": "approve" }, ... ],
  "parallel_groups": [ { "stage_index": 3, "branch_count": 3 }, ... ]
}
```

### Annotation Rules

| Node type | Annotation |
|---|---|
| ACTION (any protocol) | `parallelism: 1`, both wait flags false |
| VARIABLE | `parallelism: 0` (runs in workflow code, not as activity) |
| IF | `branch_count: 2` |
| PARALLEL (compete: false) | `parallelism: N` (N = branch count), `branch_count: N` |
| PARALLEL (compete: true) | `parallelism: N`, `branch_count: N`, note `compete: true` |
| WAIT (mode: timer) | `is_timer_wait: true` |
| WAIT (mode: signal) | `is_signal_wait: true`, records `signal_name` |
| WORKFLOW (type: child) | `parallelism: 1` |

## 6. Stage 5: Generator

### Purpose

Transform the `WorkflowIR` into a Zigflow YAML string and a Zigflow JSON string. This is the only stage that knows about Zigflow DSL syntax.

The Generator is template-driven. Each node type has one or more YAML template files in `registry/templates/`. The Generator loads the template, substitutes values from the `IRTask`, and assembles the complete `document` + `use` + `do` structure.

### Input
`WorkflowIR` + template files from Template Registry.

### Output
`dsl_yaml` (string) + `dsl_json` (string, same content different format).

### Template Structure

A template is a YAML file that represents the Zigflow task structure for one node type. Placeholder syntax uses `{{double_braces}}`.

**Example: `templates/action_http.yaml`**
```yaml
call: http
with:
  method: "{{config.method}}"
  endpoint: "{{config.endpoint}}"
  {{#if config.headers}}
  headers: {{config.headers}}
  {{/if}}
  {{#if config.body}}
  body: {{config.body}}
  {{/if}}
{{#if config.retry}}
retry: "${ $workflow.retries.{{config.retry}} }"
{{/if}}
{{#if config.outputKey}}
output:
  as: "${ $context + { {{config.outputKey}}: . } }"
export:
  as: "${ $context + { {{config.outputKey}}: . } }"
{{/if}}
```

**Example: `templates/wait_signal.yaml`**
```yaml
listen:
  to:
    one:
      with:
        id: "{{config.signalName}}"
        type: "{{config.signalType}}"
{{#if config.outputKey}}
export:
  as: "${ $context + { {{config.outputKey}}: . } }"
{{/if}}
```

### Template Selection Dispatch

The Generator selects the template for each `IRTask` using this dispatch table:

| node_type | condition | template |
|---|---|---|
| ACTION | config.protocol == "http" | action_http |
| ACTION | config.protocol == "grpc" | action_grpc |
| ACTION | config.protocol == "script" | action_script |
| ACTION | config.protocol == "shell" | action_shell |
| VARIABLE | — | variable_set |
| IF | — | if_switch |
| PARALLEL | compete == false | parallel_fork_all |
| PARALLEL | compete == true | parallel_fork_compete |
| WAIT | config.mode == "timer" | wait_timer |
| WAIT | config.mode == "signal" | wait_signal |
| WORKFLOW | config.type == "child" | workflow_child |
| WORKFLOW | config.type == "external" | workflow_external |

### Assembly Algorithm

```
Algorithm Generator(ir):
  1. Build document block:
     {dsl: "1.0.0", taskQueue: ir.task_queue, workflowType: ir.workflow_type, version: ir.version}
  2. Build use block:
     For each entry in ir.use.retries → emit use.retries block
  3. Build do list:
     For each IRTask in ir.tasks (recursive for nested branches):
       a. Select template from dispatch table
       b. Substitute config values into template
       c. If node_type is IF:
          - Render true-branch tasks recursively → embed in switch.when.then.do
          - Render false-branch tasks recursively → embed in switch.default.then.do
       d. If node_type is PARALLEL:
          - For each parallel_branch: render tasks recursively → embed in fork.branches[N].do
       e. Append {task_name: rendered_task} to do list
  4. Assemble final YAML:
     {document: ..., use: ..., do: [...]}
  5. Serialize to YAML string (using ruamel.yaml to preserve block style)
  6. Serialize to JSON string
```

### Naming Tasks in the `do` List

Each task in the Zigflow `do` list is a dict with one key: the task name. The task name becomes the key by which the task's output is accessed via `$data` in the next task.

Task name derivation:
```
1. Sanitize node label: strip non-alphanumeric, replace spaces with "_", lowercase
2. Deduplicate: if "fetch_user" already appears, use "fetch_user_2"
3. Result: "fetch_user" → key in do list
```

## 7. IF/SWITCH Special Case

The Zigflow `switch` task nesting is the most complex generator case. The exact DSL structure is unverified (see `node_registry_spec.md` — Section 3.5). Assuming Structure A (inline `do` blocks):

```yaml
# Generated from IF node "is_active" with 2 branches
- is_active:
    switch:
      - when: "${ $context.user.active == true }"
        then:
          do:
            # All true-branch IRTasks rendered here
            - send_notification:
                call: http
                ...
      - then:
          # Default (false) case — no "when" condition
          do:
            # All false-branch IRTasks rendered here
            - flag_inactive:
                set:
                  status: "inactive"
```

**Risk:** If Zigflow uses Structure B (task reference jumps) instead, the generator must emit true/false branch tasks at the top level of the `do` list and use jump references in the switch. This would require the IR and Generator to be restructured.

**Resolution strategy:** Build a minimal 3-node POC (START → IF → [VARIABLE, VARIABLE] → END) and test both DSL structures against `zigflow validate` before finalizing the generator design.

## 8. Template Engine Alternatives

### Alternative A: Jinja2

**Pros:** Mature, widely used, powerful (conditionals, loops, filters, macros). Already available as a FastAPI transitive dependency.
**Cons:** Jinja2 escaping and YAML indentation do not mix well. YAML is whitespace-sensitive; Jinja2 is whitespace-agnostic. A `{% for %}` loop in a YAML template often produces incorrect indentation. Workarounds (trim_blocks, lstrip_blocks) are error-prone.

**Risk:** Jinja2 is the wrong tool for YAML generation because YAML's structure is indentation-based, not text-based.

### Alternative B: Python dict builder (no templates)

**Pros:** No whitespace issues. The generator builds Python dicts directly and serializes to YAML at the end. Complete control over the output structure.
**Cons:** The dict-building logic becomes hard to read and hard to maintain when nested structures (switch/fork) are involved. Adding a new node type requires code changes (no data-driven flexibility).

### Alternative C: YAML blueprint files with custom `{{}}` substitution (proposed)

**Pros:** YAML files are readable as YAML. The substitution is simple key-value replacement, not a full template engine. Preserves YAML structure.
**Cons:** Conditionals (`{{#if}}`) require a lightweight template parsing step — a custom mini-engine. Deep conditionals are fragile.

### Alternative D: ruamel.yaml object model

**Pros:** Build the entire DSL as a Python object tree using ruamel.yaml's `CommentedMap` and `CommentedSeq`. Then dump to YAML with full control over block vs flow style, comments, and quoting.
**Cons:** ruamel.yaml's API is verbose. No separation between structure (where tasks go) and content (what a task looks like).

**V1 recommendation:** **Alternative B** (Python dict builder) for V1 simplicity and correctness. Migrate to Alternative C (YAML blueprints) in V2 when the number of node types grows and maintainability becomes the primary concern. Use `ruamel.yaml` for serialization in both cases (it preserves block style better than PyYAML).

## 9. Compiler Risks and Unknowns

| Risk / Unknown | Impact | Resolution |
|---|---|---|
| Zigflow `switch` task structure is unverified (Structure A vs B) | Major — affects IR Builder and Generator design | Build POC: validate minimal IF graph with `zigflow validate` |
| Zigflow `fork` branch result shape for `compete: false` (array? dict?) | Medium — affects IR and Generator for PARALLEL | Read Zigflow worker source or test empirically |
| Convergence point detection algorithm correctness for complex branch topologies | High — incorrect grouping produces wrong YAML nesting | Write unit tests for IR builder with 5+ complex graph fixtures |
| Task name collision after sanitization ("Fetch User" and "fetch_user" both → "fetch_user") | Low — generator must deduplicate with suffix counter | Easy to implement; include in generator unit tests |
| Non-deterministic topological sort order when multiple nodes have the same in-degree | Low — Kahn's algorithm is deterministic given a consistent tie-breaking rule (sort by node id alphabetically) | Specify sort order in algorithm and test with parallel-input graphs |
| VARIABLE node `set` task is a Temporal Workflow code step (no activity) — must be deterministic | Medium — if the VARIABLE config uses non-deterministic expressions (e.g., wall clock), the workflow fails | Document that VARIABLE configs must use `${ uuid }` and `${ timestamp }` only |
